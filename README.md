# Офлайн Переводчик EN ↔ RU

**OfflineTranslator** — десктопное приложение для перевода между английским и русским языками, которое работает **полностью офлайн**. Под капотом — предобученные нейросети [MarianMT](https://huggingface.co/Helsinki-NLP) от Helsinki-NLP, плюс локальный словарь терминов, который имеет приоритет над нейросетью.

Приложение не требует интернет-соединения, API-ключей и отправки текста на сторонние серверы — весь перевод выполняется на вашей машине (CPU или GPU).

## Возможности

- 🌐 **Двусторонний перевод** — поддержка направлений EN→RU и RU→EN.
- 🔀 **Выбор направления** — выпадающий список «EN → RU» / «RU → EN» и кнопка «Сменить местами» (меняет поля и направление перевода).
- ✈️ **Полностью офлайн** — после первичной загрузки моделей интернет не нужен; приватность и независимость от API.
- 📖 **Локальный словарь терминов** (`dictionary.json`) — при **точном совпадении** слова/фразы перевод берётся из словаря, а не из нейросети (полезно для терминологии). Словарь двунаправленный: пары находятся и в направлении EN→RU, и в направлении RU→EN.
- 🖥️ **Современный интерфейс** на [CustomTkinter](https://github.com/TomSchimansky/CustomTkinter) (тёмная тема).
- ⚙️ **Перевод в фоновом потоке** — окно не «зависает» во время загрузки модели и самого перевода.
- 🎮 **GPU / CPU** — автоматически использует CUDA, если доступна видеокарта, иначе работает на CPU.
- 📋 **Копирование перевода** в буфер обмена в один клик.
- 📦 **Сборка в автономный EXE** (Windows) через PyInstaller — см. `build.bat`.

## Как работает приложение

1. При запуске приложение показывает окно и **в отдельном потоке** загружает нейросети, чтобы не блокировать интерфейс.
2. При **первом** запуске модели скачиваются с HuggingFace Hub и кэшируются в **постоянной директории пользователя** — Windows: `%LOCALAPPDATA%\OfflineTranslator\cache`, Linux/macOS: `~/.cache/OfflineTranslator/cache` (не зависит от рабочей директории; обычно это занимает 2–5 минут). Последующие запуски — полностью офлайн и заметно быстрее.
3. Одновременно загружается `dictionary.json` (snapshot словаря: логические пары EN↔RU и двунаправленная таблица точного поиска).
4. При нажатии «Перевести» текст отправляется в фоновый поток:
   - сначала проверяется словарь (точное совпадение) — при наличии пары возвращаем перевод из словаря;
   - иначе текст разбивается на предложения и каждое переводится нейросетью (ограничение 512 токенов, beam search).
5. Результат возвращается в основной поток и выводится в поле перевода.

> 💡 Если вы хотите «закрепить» конкретный перевод термина, добавьте пару слов в `dictionary.json` — словарь сработает в первую очередь.

│                         #   и какая выбрана; без загрузки, без сети)
├── dictionary_manager.py # Словарь: общий core (snapshot) + DictionaryManager —
│                         #   единственный писатель dictionary.json (пары 1:1,
│                         #   атомарное сохранение, импорт/экспорт)
├── history.py            # Модуль истории переводов на SQLite: хранение последних
│                         #   50 переводов, удаление, экспорт в CSV
├── benchmarks/           # Этап 7: воспроизводимый бенчмарк Marian vs Hy-MT2 GGUF
├── dictionary.json       # Пользовательский словарь терминов (EN↔RU)
├── requirements.txt      # Зависимости Python
├── build.bat             # Скрипт сборки EXE через PyInstaller (Windows)
└── README.md             # Документация

Сгенерируются во время работы (не коммитятся):
- `history.db` — база данных истории переводов (создаётся модулем `history.py`).

Кэш моделей хранится **вне** проекта — в постоянной директории пользователя (см. «Модели перевода» ниже).

Требуется Python 3.9+.

```bash

.venv\Scripts\activate
# Linux/macOS:
source .venv/bin/activate

pip install -r requirements.txt
```

## Модели перевода

Используются предобученные модели Helsinki-NLP:

- `Helsinki-NLP/opus-mt-en-ru` — английский → русский;
- `Helsinki-NLP/opus-mt-ru-en` — русский → английский.

Модели загружаются с HuggingFace Hub при первом запуске и кэшируются в **постоянном пользовательском кэше** — местоположение фиксированное, не зависит от рабочей директории (CWD):

- Windows: `%LOCALAPPDATA%\OfflineTranslator\cache`;
- Linux/macOS: `$XDG_CACHE_HOME/OfflineTranslator/cache` (если переменная не задана — `~/.cache/OfflineTranslator/cache`).

GGUF-бэкенд (Этап 6, CPU-POC): `tencent/Hy-MT2-1.8B-GGUF` (напр. `Hy-MT2-1.8B-Q4_K_M.gguf`, ~1.1 ГБ) — **локальный файл**, скачивания нет: путь задаётся переменной окружения `OFFLINE_TRANSLATOR_GGUF`, бэкенд выбирается через `OfflineTranslator(backend="llama_cpp", gguf_path=...)`. По умолчанию (`OfflineTranslator()`) используется Marian-бэкенд — поведение не изменилось.

### Реестр моделей (`model_registry.py`, Этап 8)

Backend-нейтральный слой «какие модели существуют и какая выбрана» — следующий этап подключит к нему GUI, не зная деталей движков:

- `ModelDescriptor` — лёгкое описание модели (id, имя, backend, направления, происхождение). Описывает модель, но **не загружает** её;
- `ModelRegistry` — набор моделей: `get()`, `list()`, `find_by_backend()`, `find_by_direction()`; уникальные id, детерминированный порядок;
- `ModelManager` — состояние на этой машине: `get_available_models()`, `get_model()`, `is_model_available()`, `get_default_model(direction)`, `resolve()`.

Доступность определяется **без загрузки модели** и без сети (download-функций нет): Marian — по локальному HF-кэшу (см. выше), GGUF — по файлу из `OFFLINE_TRANSLATOR_GGUF`. Зарегистрированные model id: `marian-en-ru`, `marian-ru-en` (Marian — две независимые модели Helsinki-NLP, по одной на направление) и `hy-mt2-1.8b` (GGUF, оба направления).

### Выбор модели в пайплайне (Этап 9)

`ModelManager` подключён к `OfflineTranslator` через параметр `model_id` — новый способ выбрать **конкретную** модель (legacy-способ `backend=` сохранён):

```python
OfflineTranslator()                                        # по умолчанию — Marian (без изменений)
OfflineTranslator(backend="marian")                        # legacy: Marian
OfflineTranslator(backend="llama_cpp", gguf_path="...")    # legacy: GGUF
OfflineTranslator(model_id="marian-en-ru")                 # новый: конкретная модель
OfflineTranslator(model_id="hy-mt2-1.8b", gguf_path="...") # GGUF: gguf_path или OFFLINE_TRANSLATOR_GGUF
```

Правила: `model_id` и `backend` одновременно задавать нельзя (`ValueError`); неизвестный id — `ModelNotFoundError` (со списком известных); модель отсутствует локально — `ModelUnavailableError` (скачивание **не** выполняется, в сообщении — где ожидается источник); `gguf_path` к не-GGUF-модели — `ValueError`. Выбранная через `model_id` модель ограничивает направления: `translate()`/`translate_stream()` в неподдерживаемом направлении — явная ошибка, а не тихий перевод не в том направлении (legacy-режим без `model_id` — без ограничений, как раньше).

### Выбор модели в приложении (Этап 10)

GUI подключён к реестру без знания движков: окно «Настройки» → «Модель» строит список из `ModelManager` (дескрипторы + **лёгкая** проверка локальной доступности — без импорта/создания inference-бэкендов и без сети; источник — `test_llama_cpp_backend.py`, чек `gui_no_engine_words`). В списке видно имя модели, локальную доступность; неподдерживаемые текущим направлением модели помечены. Выбор применяется по «Сохранить» без перезапуска: сохраняется в `settings.json` (`model_id`), при необходимости переводчик (пере)загружается в фоне.

Устаревший/проблемный выбор обрабатывает `ModelManager.resolve_runtime(saved_model_id, direction)` (только дескрипторы + filesystem, без сети и загрузки):

- неизвестный id или модель не поддерживает направление → модель по умолчанию для направления (исправленное значение сохраняется в настройки);
- модель недоступна локально, дефолт направления доступен → запускается дефолт, **выбор пользователя не меняется** (модель может появиться позже — напр. положат GGUF-файл), заметка показана в статусе; скачивания нет;
- ни одна модель не поддерживает направление → `ModelNotFoundError` (ошибка загрузки видна в статусе).

Текущая (запущенная) модель видна в подзаголовке окна и в статусе «Готов к переводу! (… модель: …)». Смена направления учитывает модель: несовместимая модель автоматически заменяется дефолтом направления.

Интерфейс перевода (одно окно, два поля):

- **Подсветка пар** — в любой момент подсвечена ровно одна пара «предложение k ↔ его перевод»: во время перевода — последняя завершённая; hover/клик в любом из полей — пара под курсором в обоих полях; при уходе мыши — назад на стрим-юнит (во время перевода) или сброс. Сопоставление — только по смещениям пайплайна (unit-индексы/offsets из `sentence_pipeline`), сопоставление по тексту не используется. Mapping сбрасывается при очистке/swap/смене направления/модели/редактировании текста.
- **Синхронная прокрутка** — двусторонняя: любое изменение вида одного поля (wheel, клавиши, скроллбар, программное) выставляет в другом ту же относительную позицию документа (yview-фракция). Синхронизация — через синхронный `yview_moveto()` с re-entrancy-защитой (callback партнёра срабатывает в момент вызова и блокируется, рекурсивных циклов нет); wheel-события покрыты на всех платформах, включая Linux (`<MouseWheel>`, `<Button-4>`, `<Button-5>`). Ручная прокрутка отключает автопоказ текущей пары (возвращается при следующем запуске перевода).
- **Схема оформления (Этап 12)** — в «Настройках» дропдаун «Схема оформления» с пояснением: тёмная — комфортнее при слабом освещении, светлая — выше яркость и контраст. Выбор сохраняется в `settings.json` (`theme`) и по «Сохранить» применяется сразу, без перезапуска (окно, диалог, текстовые поля, подсветка).
- **Форматирование перевода (Этап 12)** — приложение не вставляет переносы строк по фиксированной длине: в поле вывода попадают только логические переводы (предложения внутри абзаца — пробелом, абзацы — `"\n\n"`, границы — из `new_paragraph` пайплайна). Перенос длинных строк по ширине окна — **визуальный**, выполняется самим `Text` (`wrap="word"`), фактический текст и смещения `_unit_map` от размера окна не зависят: подсветка, hover и синхронная прокрутка работают после resize.

### Инкрементальный кэш перевода (Этап 13)

Повторный перевод изменённого исходного текста (автоперевод при редактировании) не отправляет в модель неизменённые предложения: переводы логических юнитов кэшируются в памяти, в inference уходят только изменённые/новые юниты.

- кэш **только в памяти** (`translation_cache.TranslationCache` внутри `TranslationService`): нет SQLite/дисковой персистентности/Redis, нет LRU и семантического сопоставления; при перезапуске приложения он пуст;
- ключ: **(модель, направление, точный текст юнита)** — позиция юнита в тексте в ключ не входит: вставка/удаление/переупорядочение других предложений не инвалидирует результаты; дубликаты юнитов разделяют одну запись;
- результат одной модели/направления не используется для другой: смена направления или модели — полный новый перевод;
- словарь (`dictionary.json`) не кэшируется: точное совпадение всего текста имеет приоритет и проверяется до кэша;
- контракт стрима не меняется: юниты-попадания выдаются сразу (backend не вызывается), промахи — обычным путём через backend; порядок start/done-событий, границы абзацев и финальный текст от кэша не зависят;
- GUI и пайплайн не меняются: кэш прозрачен для `translate()`/`translate_stream()`.

Кэш сохраняет стандартную структуру HuggingFace. Удаление этой папки приведёт к повторной загрузке моделей при следующем запуске (для EXE со встроенными моделями — восстановлению из бандла).

## Формат словаря

Словарь хранится в `dictionary.json` в неизменном flat-формате «ключ → перевод»: логическая пара (EN, RU) записывается двумя зеркальными записями:

```json
{
    "workspace": "рабочее пространство",
    "repository": "репозиторий",
    "рабочее пространство": "workspace",
    "репозиторий": "repository"
}
```

- Ключи нормализуются `strip()` + `lower()`, значения — `strip()` (регистр сохраняется); lookup регистронезависим.
- Словарь **двунаправленный**: пара находится в обоих направлениях (EN→RU и RU→EN); направление перевода влияет только на выбор нейросетевой модели.
- Политика 1:1: у термина ровно один партнёр (нельзя иметь `car → «машина»` и `vehicle → «машина»` одновременно); зеркало той же пары (`a → b` и `b → a`) конфликтом не считается.
- Словарь срабатывает только при **точном совпадении** всего введённого текста.

В `dictionary_manager.py` — единственная реализация нормализации и загрузки (snapshot) и класс `DictionaryManager`, единственный писатель `dictionary.json`: `add`, `edit`, `delete`, `search`, `get_all`, `get_count`, `import_from_json`, `export_to_json`, `reload`, `find_conflict`. Сохранение атомарное (временный файл + `os.replace`); `OfflineTranslator` не хранит словарь в памяти и читает свежий snapshot в начале каждого `translate()`, поэтому изменения видны без перезапуска приложения. В development путь к словарю — `dictionary.json` в корне проекта; для EXE — `%LOCALAPPDATA%\OfflineTranslator\dictionary.json` (на Unix — user-директория; при первом запуске bundled-копия копируется туда, существующий словарь не перезаписывается). Аналогично, `history.py` реализует хранение и экспорт истории переводов.

## Сборка автономного EXE (Windows)

В корне проекта есть скрипт `build.bat`, который:

1. устанавливает `pyinstaller`;
2. очищает старые артефакты сборки;
3. проверяет кэш моделей: если `cache\` заполнен (или модели уже есть в пользовательском кэше `%LOCALAPPDATA%\OfflineTranslator\cache`), копирует их в проект и встраивает в EXE;
4. собирает приложение в один исполняемый файл.

```bat
build.bat
```

Готовый файл появится в папке `dist\OfflineTranslator.exe`.

> ⚠️ EXE встраивает модели, только если они уже скачаны (в `cache\` или в пользовательском кэше). Иначе EXE скачает модели при **первом** запуске (нужен интернет), после чего будет работать полностью офлайн.
>
> При первом запуске EXE встроенные модели копируются в `%LOCALAPPDATA%\OfflineTranslator\cache`; временная директория PyInstaller (`_MEIPASS`) в качестве кэша **не** используется.
